# Literature review: autonomous software-engineering agents

Research cutoff 2026-11-20. Compiled 2026-11-21.

Target setting: one Gemma 4 model (31B / 12B / E4B / E2B, 4-bit), 32k context, about 5 minutes and about 40 tool calls per task, tools = shell, read_file, edit_file, write_file, 3 code-graph tools, submit_patch. Submission is declarative only (YAML + prompts + optional skills scripts + optional LoRA adapters), single model, offline.

## How verification was done (read this first)

- Direct fetching of arxiv.org is blocked from this machine. Every item was checked through web search only. "Verified" means a search returned the paper's own page (arXiv abs/html/pdf, ACL Anthology, publisher, or official repo) with a matching title, and the numbers quoted below appeared in the search engine's extract of that page. **I did not read any full paper.** Experimental details, ablations and caveats beyond the abstract level are therefore unchecked.
- "Reported evidence" contains only numbers seen in those extracts. Where a number came from a secondary source (blog, aggregator) it is flagged.
- Anything labelled **Hypothesis** is my inference for this competition, not a reported result.
- None of the papers below evaluates Gemma 4, a 32k context cap, a 5-minute limit, or a 40-call limit. Every transfer claim to this setting is a hypothesis until measured on a local dev set.

## Decisions

Evidence strength scale: **strong** = multiple independent verified sources with numbers; **moderate** = one verified source with numbers, or several sources in different settings; **weak** = single small study or indirect; **none** = my hypothesis. Every item is a hypothesis as applied to Gemma 4 at 32k / 40 calls / 5 minutes.

### Ranked techniques that fit the declarative submission

1. **Fixed localization funnel with a hard exploration cap (system prompt).**
   Form: "Calls 1-8: locate. Use the code-graph tools on symbols named in the issue or traceback first, then one batched grep. Read at most 80 lines per read_file, with explicit line ranges. By call 10 you must have named one file and one function to change." 
   Evidence: moderate. SWE-Explore (early coverage within a tight line budget is the best predictor of repair, rho 0.845); Agentless (hierarchical localization); cost-effective-exploration paper (cheap models retain most localization quality). The specific call numbers are my hypothesis.

2. **Syntax/AST gate after every edit (skills script).**
   Form: a script such as `skills/check.sh <file>` that runs `python -m py_compile` (optionally `pyflakes` if present offline) and prints at most 10 lines; the prompt requires it after each `edit_file`/`write_file` and forbids submitting while it fails. Extend the same script to print `git diff --stat` so the model sees unintended changes.
   Evidence: moderate. SWE-agent's linter-gated edit is a documented core ACI feature (ablation delta not captured); failure taxonomies say weaker models fail mainly on syntax and tool use.

3. **Verify with existing tests before submit, output-capped (prompt + skills script).**
   Form: `skills/run_tests.sh <path>` wrapping `python -m pytest <nearest test file> -x -q --tb=short 2>&1 | tail -n 30` with a `timeout 60`. Run once before editing only if cheap, and once after. A new failure in previously passing tests means revert or fix.
   Evidence: moderate. Regression-test filtering improved Agentless by a relative 9.4-12.9%; SWE-agent data show submitted (vs budget-exhausted) trajectories resolve far more often.

4. **Reproduction-first, but time-boxed to two calls (prompt).**
   Form: "If the issue contains a snippet or traceback, reproduce it with one `python -c`/script call. If it does not reproduce in two calls, stop trying and proceed from code reading." 
   Evidence: moderate that reproduction tests help when they exist (Otter); moderate that generating them is unreliable (best systems 37-63% fail-to-pass, with frontier models). The two-call cap is my hypothesis, motivated by the 40-call limit.

5. **Two zero-cost reasoning checkpoints from DeskCheck (prompt).**
   Form: before the first edit, write the execution path from the issue's entry point to the faulty line in at most 5 lines; before `submit_patch`, list each requirement in the issue next to the diff hunk that satisfies it, and fix any gap.
   Evidence: moderate for the full scaffold (+6.29 to +10.53 on SWE-bench-Pro, but with much stronger models and five stages); weak for this two-step reduction.

6. **Observation diet and file-backed notes (prompt + YAML).**
   Form: every shell command ends in a size cap (`head`, `tail`, `grep -n -m`); never `cat` a file; never print full test logs. Keep a 10-line notes file with hypothesis, target, test command, attempts. Turn on any harness-side observation truncation or history limits available in YAML.
   Evidence: strong that observations dominate context (about 84% of tokens) and that dropping old ones does not hurt solve rate (Complexity Trap); moderate for state/evidence separation (Semantic Context Handoff, +6.9 points from recoverable evidence in its own setting). Whether a small model maintains notes reliably is untested.

7. **Anti-loop and always-submit rules, plus a single-agent YAML with conservative sampling (prompt + YAML + budget settings).**
   Form: "Never repeat a command that already failed unchanged. After two failed edits at the same location, re-read the lines and change approach. From call 30 onward, stop exploring: finalize the smallest working diff. Always call submit_patch before the budget ends; a plausible minimal patch beats no patch." YAML: one agent, no planner/reviewer roles, low temperature (0-0.3), max-turns set just under the hard limit so the final call is reserved for submit, per-command timeouts.
   Evidence: moderate for the diagnosis (SWE-agent: repeated actions cascade, submit-ending runs 14.3% vs 3.1%; SWE-Protege and SWE-EVO: looping is the characteristic small-model failure). None for the specific thresholds or for budget-reminder prompts; none found for sampling temperature in this setting.

8. **LoRA on short, successful, in-harness trajectories (LoRA SFT data).**
   Form: SFT data in the exact tool schema and system prompt of the submission; only resolved trajectories; at most about 30 tool calls and fitting in 32k tokens; loss on assistant turns only; drop "lucky pass" trajectories (no verification step, blind retries); oversample tasks the base model fails and a teacher solves. Sources to convert: SWE-smith trajectories, SWE-Gym, R2E-Gym; better, trajectories generated in the actual Kaggle harness.
   Evidence: strong that trajectory SFT helps 32B-class models with full fine-tuning (SWE-Gym +13.6 with 491 trajectories; SWE-smith 40.2%; R2E-Gym 34.4%; Nemotron reports). Weak for LoRA specifically and for small tiers (7B-scale LoRA study reports near-zero resolve rates). Risk: a format mismatch between public trajectories and our tools can make the adapter worse than the base model. Treat as the highest-variance item and gate it on a local A/B.

Lower-priority items that also fit:

9. **Batched search in one shell call** (CodeGrep-style parallel grep). Evidence: none for the prompt-only version.
10. **Edit hygiene from Aider**: re-read exact lines before `edit_file`, small replaced spans, `write_file` only for small files. Evidence: weak (docs say weak models do better with whole-file edits; no numbers for our tool).
11. **Requirement-traced harness changes with a held-out split** (AHE-Beta as a process). Evidence: weak (38 tasks).
12. **Model choice**: prefer the largest tier that finishes within 5 minutes. Evidence: weak (timeout-cascade paper says the small/large gap sits on hard tasks; 7B-scale models near zero without help). Tokens-per-second of each 4-bit tier on the Kaggle hardware must be measured; I found no Gemma 4 coding-agent benchmark numbers.

### Popular ideas that do not fit 5 minutes / 40 calls / 32k / one model

- **Best-of-N patches with test-based or LLM selection** (CodeMonkeys, Agentless voting, R2E-Gym hybrid verifiers, SWE-Gym verifier). Needs N full attempts plus selection; reported budgets are hundreds of calls or thousands of dollars per benchmark, and gains scale roughly log-linearly with samples. One 5-minute attempt leaves room for N = 1. Selection also needs orchestration code.
- **Search over trajectories** (SWE-Replay, MCTS-style search, reward-model-guided search in SWE-Reasoner). Requires branching, state snapshots and an archive: custom orchestration.
- **Process reward models and learned verifiers** (SWE-PRM, SWE-RM). A second model or a second inference stream; one model per submission and no spare latency.
- **Separate trained explorer or retrieval agent** (CodeGrep, FastContext). Second model, RL training.
- **Model cascades and routing** (Timeout Cascades). Two models; optimizes cost rather than resolve rate.
- **Expert-assisted small models** (SWE-Protege). Needs an online stronger model.
- **Multi-agent role teams** (MAGIS, HyperAgent, Agyn). Each handoff re-spends context and calls and risks losing information; published gains come without tight call limits.
- **LLM summarization of history.** Costs extra generation time and performs no better than simple masking (Complexity Trap).
- **Full five-stage DeskCheck, or full Agentless pipelines.** Stage count and sampling exceed the call budget; only the compressed forms above fit.
- **Self-play / RL training loops** (SWE-growth, GRPO). Needs executable environments at scale and a teacher; only the data-selection idea carries into a LoRA.
- **Comprehensive generated test suites** before patching. State-of-the-art fail-to-pass rates are 37-63% with frontier models; for a 4-bit small model the expected return per call is low. Keep to the two-call reproduction rule.
- **Automated harness evolution** (AHE, Meta-Harness) as a runtime feature. It is a development-time process; nothing of it ships in the submission.
