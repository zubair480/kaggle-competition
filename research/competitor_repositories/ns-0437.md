## Verdict in one line

A 31B coder + read-only analyzer agent that scored **0.06 three times in a row** (v1, v2, v3), wrapped in very heavy evidence tooling. Its value to us is the documented failure modes of the harness and of Gemma under a long prompt, not the agent design.

## Architecture (implemented)

- Model: `gemma-4-31b-it-qat-w4a16-ct` for both agents.
- Root `swe_coder`: `run_command`, `read_file`, `edit_file`, `write_file`, `get_status`, `submit_patch` + `agent_tool` -> `code_analyzer` (`skip_summarization: true`). v1 also gave the root the three graph tools; v2 onward moved them to the analyzer only.
- `code_analyzer`: read-only, `run_command`, `read_file`, 3 graph tools; "at most about 12 tool calls"; fixed answer format `FILES / EVIDENCE / FIX / TESTS / CONFIDENCE`, at most 200 words.
- Sampling (shared): temp 0.2, top_p 0.95, top_k 40, `max_output_tokens` 8192, `seed: 42`, `thinking_budget` 4096, **`include_thoughts: false`**.
- **No `eval_config.yaml` in any release**, so scored runs used whatever the harness/starter defaults were. Local pilot budgets were 10 min / 100 tool calls / 60 turns / 300 s commands.
- No skills, no adapters.

## Prompt summary

Working prompt `submission/prompts/system.md` is 935 words (v1 684, v2 607, pilot 737, v3 reported 1,247). Six-step workflow Understand / Localize / Reproduce / Fix / Verify / Submit. Notable verbatim rules:

- "`write_file` and `edit_file` can ONLY write inside /workspace; they reject /tmp with a path-traversal error. Create scratch files with `run_command` and a shell heredoc"
- "**Confirm you are testing the checkout, not an installed copy**, before trusting any result: `cd /workspace && python3 -c "import <pkg>; print(<pkg>.__file__)"`. The path must be under /workspace. If it is not, re-run with `PYTHONPATH=/workspace/src`"
- Exit-code-preserving test command:
  ```
  python3 -m pytest <test file> -q -x > /tmp/test-output.txt 2>&1; result=$?; tail -60 /tmp/test-output.txt; echo "PYTEST_EXIT_CODE=$result"
  ```
- "Exit code 5 means no tests collected, not success. A skipped test does not verify the fix."
- "Available: git, grep, find, sed, awk, python3. Not available: rg, tree."
- "**If any changed path is a test path** ... restore it before anything else: `git checkout -- <path>` ... The graders replace those files, so an edit there cannot help you and can stop your work being graded at all."
- "New untracked source files do not appear in ordinary `git diff`: inspect their contents explicitly."
- "If two searches do not improve your understanding, change strategy"
- Analyzer notes: "`get_code_neighbors` / `get_code_subgraph`: synchronous "calls" edges only; async functions are missing from the graph." and "`search_similar_code` takes a symbol name (e.g. `APIKeyHeader`), not a sentence; its ranking is imprecise."

## Weaknesses

- Never obtained a single locally graded agent run, so every design decision is unvalidated.
- No explicit `eval_config.yaml`; time/tool-call behaviour in scored runs is unknown and may be the reason for 0.06 (the sample submission default is 1 min / 10 calls per the harness guide; which default applied to their scored runs is not stated).
- Long prompt (935-1,247 words) plus analyzer; the author's own next hypothesis was to cut the prompt to 413 words. Outcome never recorded (repo went quiet 2026-09-30).

## Ideas worth adopting

1. **Import-provenance check before trusting a repro**: one `python3 -c "import pkg; print(pkg.__file__)"` call. In their subprocess evaluation the runtime imported an installed copy instead of the checkout, so a "passing" repro validated the wrong code. Cheap insurance; fold it into the first repro command rather than a separate call.
2. **Exit-code-preserving test command and "exit 5 = nothing collected"**. Piping pytest through `tail` hides the exit status; a small model then reads a truncated tail as success.
3. **Scratch files via heredoc in `/tmp`, because `write_file`/`edit_file` reject paths outside `/workspace`**. A model that hits the rejection tends to move the scratch file into the repo, which then lands in the patch.
4. **Pre-submit test-path restore** (`git diff --name-only` then `git checkout -- <test path>`), and explicit check of untracked new source files. Both traced pilot runs edited test files.
5. **Loop guard wording**: "do not re-run the same command hoping for a different answer". Repetition loops (25x and 56x identical calls) were their dominant observed failure. Also set `max_tool_calls` low enough that a loop cannot eat the whole budget.
6. **Tool facts for the prompt**: no `rg`/`tree`; `search_similar_code` wants a symbol, not a sentence; graph tools miss async functions.

## Ideas to reject

1. **Coder + analyzer sub-agent as the default design.** 0.06 three times here; repo B's single agent is reported at 0.17 on the same model. Not a controlled comparison, but there is zero positive evidence for the analyzer.
2. **Omitting `eval_config.yaml`.** Budgets must be explicit.
3. **A 900-1,200 word workflow prompt.** Their own traces show loops and no patch; their own follow-up hypothesis was a 3x shorter prompt.
4. **`include_thoughts: true` without a context check.** Their single thinking-on run used 3.6x the prompt tokens and overflowed the 32k window. n=1, so treat it as a risk to test, but note that repos A and B both ran `include_thoughts: true` and B's 0.17 config uses it; the overflow here coincided with a 100-call budget and a repeat loop. The actionable point is the interaction: thoughts in history + many calls + 14k compaction threshold.
5. **Building evidence infrastructure before having one graded run.** The project spent its whole life on tooling and ended with no measurement.
